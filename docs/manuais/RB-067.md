## 4. Passo a passo da tarefa

1. Monte matriz de falhas para timeout, rate limit, IA indisponível, callback repetido, concorrência e banco indisponível.
2. Injete falha antes e depois do efeito externo para diferenciar recusa de resultado incerto.
3. Verifique consulta/reconciliação após perder resposta e após reiniciar processo.
4. Exercite retry limitado e repetição concorrente, contando pedidos/cobranças reais do ambiente de teste.
5. Registre defeitos e retestes com IDs sanitizados; não aceite apenas ausência de exceção como prova.


## 5. Como validar

Na primeira preparação, siga o [README](../../README.md) e execute `npm ci --ignore-scripts` e `npm run db:generate` antes de comandos que usem dependências. Node 22 e PHP 8.3 são as versões de referência do CI. Variáveis e segredos são locais; consulte `.env.example` e o guia do componente.

| Caso mínimo | Ação e resultado a verificar | Registro |
| --- | --- | --- |
| V1 | Falha depois de cobrar não causa segunda cobrança ao recuperar. | Não executado por este manual; registrar resultado e link na entrega. |
| V2 | Mesmo callback/evento concorrente mantém estado único; retry para ao atingir limite. | Não executado por este manual; registrar resultado e link na entrega. |

Execute na raiz, após produzir sua alteração:

```powershell
npm run check
git diff --check
```

Acrescente teste comportamental pertinente em `tests/*.test.ts`, incluído pelo runner atual, quando houver código novo. Configure apenas ambientes descartáveis/autorizados para banco, loja e PSP; fixtures não comprovam integração externa.

Para cada critério abaixo, preencha na entrega: preparação, ação, esperado, observado, passou/falhou/não executado e evidência. Para design/documentação, inclua revisão de leitura/links/protótipo; não crie teste de código artificial. Uma execução antiga não comprova seu commit atual.

## 7. Branch, documentação e PR pelo terminal

Se é seu primeiro trabalho, clone e configure autoria conforme o [tutorial](../../README.md). Dentro de `boopay`, com trabalho anterior salvo na branch correta e árvore limpa:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/rb-067-testar-falhas-idempotencia-e-recuperacao
```

Se essa branch já existe, use `git switch feat/rb-067-testar-falhas-idempotencia-e-recuperacao` para continuar; não execute `-c` novamente. Prepare seu documento sem sobrescrever uma entrega existente:

```powershell
if (-not (Test-Path 'docs/entregas/RB-067.md')) {
    Copy-Item 'docs/entregas/MODELO.md' 'docs/entregas/RB-067.md'
}
```

Faça os passos da seção 4 e preencha `docs/entregas/RB-067.md`: autor, issue, manual, objetivo, arquivos, decisões, preparação, passos, esperado/observado, evidências e pendências. Remova os campos de orientação do modelo e preserve versões anteriores. Para artefato externo, versione o roteiro/registro com link acessível, exportação ou capturas pertinentes; não abra PR vazio.

Antes de enviar, execute a seção 5 e confira seleção de arquivos:

```powershell
git diff --stat
git diff
git status --short
git add -- docs/entregas/RB-067.md
```

O comando acima seleciona apenas a documentação. Selecione também cada arquivo de código/teste/artefato que você criou ou alterou com `git add -- caminho/do/arquivo` (substitua pelo caminho real). Confira `git status --short` e não inclua `.env`, banco local, credenciais ou trabalho de outra tarefa. Depois:

```powershell
git diff --cached --check
git diff --cached
git commit -m "RB-067: Testar falhas, idempotência e recuperação"
git push -u origin feat/rb-067-testar-falhas-idempotencia-e-recuperacao
```

No GitHub, abra **Pull requests → New pull request**, base `main`, compare `feat/rb-067-testar-falhas-idempotencia-e-recuperacao`. Use o [modelo de PR](../../.github/PULL_REQUEST_TEMPLATE.md). Quem já tem GitHub CLI autenticado pode usar `gh pr create --base main --head feat/rb-067-testar-falhas-idempotencia-e-recuperacao --web` após o push.

Preencha no PR:

## 8. Quando pedir review e quando concluir

Peça revisão e mova para **Review** quando o PR tiver escopo conferível, documentação e validação anexadas. Resolva os comentários na mesma branch e repita os checks afetados. O autor não aprova o próprio PR. **Done** exige revisão, merge e validação do resultado integrado conforme o card/DoD; abrir PR ou publicar este manual não basta.

Se houver bloqueio, registre: passo que falhou, erro sanitizado, tentativa feita, dependência e ajuda necessária. Não simule sucesso para concluir o card.
