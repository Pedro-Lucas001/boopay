## 4. Passo a passo da tarefa

1. Confira cabeçalho, versão, slug e estrutura que o WordPress reconhece.
2. Valide dependência WooCommerce e versões antes de registrar recursos que as utilizam.
3. Revise ativação, desativação e desinstalação, incluindo opções e tarefas agendadas.
4. Defina quais dados são preservados na desativação e removidos na desinstalação; explique no readme do plugin.
5. Instale o ZIP gerado em loja limpa e percorra o ciclo completo.


## 5. Como validar

Na primeira preparação, siga o [README](../../README.md) e execute `npm ci --ignore-scripts` e `npm run db:generate` antes de comandos que usem dependências. Node 22 e PHP 8.3 são as versões de referência do CI. Variáveis e segredos são locais; consulte `.env.example` e o guia do componente.

| Caso mínimo | Ação e resultado a verificar | Registro |
| --- | --- | --- |
| V1 | Sem WooCommerce, há aviso compreensível e nenhum fatal. | Não executado por este manual; registrar resultado e link na entrega. |
| V2 | Desativar interrompe jobs; reativar e desinstalar seguem a política documentada. | Não executado por este manual; registrar resultado e link na entrega. |

Execute na raiz, após produzir sua alteração:

```powershell
npm run check
git diff --check
npm run package:plugin
npm run qa:plugin
```

Para testes na loja, prepare o ambiente pelo [guia WordPress](../entregas/AMBIENTE-PLUGIN.md) antes de `npm run qa:wordpress`. O QA local de PHP não substitui instalação limpa/navegação. Preserve a evidência existente; nova execução deve informar seu próprio commit e ambiente.

Para cada critério abaixo, preencha na entrega: preparação, ação, esperado, observado, passou/falhou/não executado e evidência. Para design/documentação, inclua revisão de leitura/links/protótipo; não crie teste de código artificial. Uma execução antiga não comprova seu commit atual.

## 7. Branch, documentação e PR pelo terminal

Se é seu primeiro trabalho, clone e configure autoria conforme o [tutorial](../../README.md). Dentro de `boopay`, com trabalho anterior salvo na branch correta e árvore limpa:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/rb-008-criar-estrutura-do-plugin-e-ciclo-de-ativacao
```

Se essa branch já existe, use `git switch feat/rb-008-criar-estrutura-do-plugin-e-ciclo-de-ativacao` para continuar; não execute `-c` novamente. Prepare seu documento sem sobrescrever uma entrega existente:

```powershell
if (-not (Test-Path 'docs/entregas/RB-008.md')) {
    Copy-Item 'docs/entregas/MODELO.md' 'docs/entregas/RB-008.md'
}
```

Faça os passos da seção 4 e preencha `docs/entregas/RB-008.md`: autor, issue, manual, objetivo, arquivos, decisões, preparação, passos, esperado/observado, evidências e pendências. Remova os campos de orientação do modelo e preserve versões anteriores. Para artefato externo, versione o roteiro/registro com link acessível, exportação ou capturas pertinentes; não abra PR vazio.

Antes de enviar, execute a seção 5 e confira seleção de arquivos:

```powershell
git diff --stat
git diff
git status --short
git add -- docs/entregas/RB-008.md
```

O comando acima seleciona apenas a documentação. Selecione também cada arquivo de código/teste/artefato que você criou ou alterou com `git add -- caminho/do/arquivo` (substitua pelo caminho real). Confira `git status --short` e não inclua `.env`, banco local, credenciais ou trabalho de outra tarefa. Depois:

```powershell
git diff --cached --check
git diff --cached
git commit -m "RB-008: Criar estrutura do plugin e ciclo de ativação"
git push -u origin feat/rb-008-criar-estrutura-do-plugin-e-ciclo-de-ativacao
```

No GitHub, abra **Pull requests → New pull request**, base `main`, compare `feat/rb-008-criar-estrutura-do-plugin-e-ciclo-de-ativacao`. Use o [modelo de PR](../../.github/PULL_REQUEST_TEMPLATE.md). Quem já tem GitHub CLI autenticado pode usar `gh pr create --base main --head feat/rb-008-criar-estrutura-do-plugin-e-ciclo-de-ativacao --web` após o push.

Preencha no PR:

- Relação: `Refs #23` para parcial/documentação; `Closes #23` apenas se a entrega cumpre todo o aceite. Isso vincula fechamento ao merge, não à abertura do PR.
- Link deste manual e `docs/entregas/RB-008.md`.
- Arquivos e resultado entregue; decisões relevantes e motivo.
- Passos/comandos exatos para o revisor repetir, com ambiente e dados sintéticos.
- Resultados observados, links de evidência e limitações restantes.
- Revisor combinado, diferente do autor; mantenha Draft se faltar parte obrigatória.

## 8. Quando pedir review e quando concluir

Peça revisão e mova para **Review** quando o PR tiver escopo conferível, documentação e validação anexadas. Resolva os comentários na mesma branch e repita os checks afetados. O autor não aprova o próprio PR. **Done** exige revisão, merge e validação do resultado integrado conforme o card/DoD; abrir PR ou publicar este manual não basta.

Se houver bloqueio, registre: passo que falhou, erro sanitizado, tentativa feita, dependência e ajuda necessária. Não simule sucesso para concluir o card.
