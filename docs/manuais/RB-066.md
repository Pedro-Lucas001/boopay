1. Congele fixture de duas lojas, produto/variante e resultado comercial esperado.
2. Automatize recomendação → revisão → confirmação → pagamento de teste → pedido → painel.
3. Execute a matriz de adaptadores/protocolos acordada e registre célula não executada com motivo.
4. Use IDs duráveis para conferir a mesma compra no core, loja, PSP e consultas.
5. Guarde comando, commit, ambiente, esperado/observado e relatório, distinguindo doubles de sandbox autorizado.


## 5. Como validar

Na primeira preparação, siga o [README](../../README.md) e execute `npm ci --ignore-scripts` e `npm run db:generate` antes de comandos que usem dependências. Node 22 e PHP 8.3 são as versões de referência do CI. Variáveis e segredos são locais; consulte `.env.example` e o guia do componente.

| Caso mínimo | Ação e resultado a verificar | Registro |
| --- | --- | --- |
| V1 | Jornada conclui uma compra única e a receita aparece na loja correta. | Não executado por este manual; registrar resultado e link na entrega. |
| V2 | Teste executado por outra pessoa não depende de banco pessoal ou credencial no código. | Não executado por este manual; registrar resultado e link na entrega. |

Execute na raiz, após produzir sua alteração:

```powershell
npm run check
git diff --check
```

Acrescente teste comportamental pertinente em `tests/*.test.ts`, incluído pelo runner atual, quando houver código novo. Configure apenas ambientes descartáveis/autorizados para banco, loja e PSP; fixtures não comprovam integração externa.

Para cada critério abaixo, preencha na entrega: preparação, ação, esperado, observado, passou/falhou/não executado e evidência. Para design/documentação, inclua revisão de leitura/links/protótipo; não crie teste de código artificial. Uma execução antiga não comprova seu commit atual.

## 7. Branch, documentação e PR pelo terminal

Se é seu primeiro trabalho, clone e configure autoria conforme o [tutorial](../../README.md). Dentro de `boopay`, com trabalho anterior salvo na branch correta e árvore limpa:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/rb-066-automatizar-jornada-principal-do-mvp-em-sandbox
```

Se essa branch já existe, use `git switch feat/rb-066-automatizar-jornada-principal-do-mvp-em-sandbox` para continuar; não execute `-c` novamente. Prepare seu documento sem sobrescrever uma entrega existente:

```powershell
if (-not (Test-Path 'docs/entregas/RB-066.md')) {
    Copy-Item 'docs/entregas/MODELO.md' 'docs/entregas/RB-066.md'
}
```

Faça os passos da seção 4 e preencha `docs/entregas/RB-066.md`: autor, issue, manual, objetivo, arquivos, decisões, preparação, passos, esperado/observado, evidências e pendências. Remova os campos de orientação do modelo e preserve versões anteriores. Para artefato externo, versione o roteiro/registro com link acessível, exportação ou capturas pertinentes; não abra PR vazio.

Antes de enviar, execute a seção 5 e confira seleção de arquivos:

```powershell
git diff --stat
git diff
git status --short
git add -- docs/entregas/RB-066.md
```

O comando acima seleciona apenas a documentação. Selecione também cada arquivo de código/teste/artefato que você criou ou alterou com `git add -- caminho/do/arquivo` (substitua pelo caminho real). Confira `git status --short` e não inclua `.env`, banco local, credenciais ou trabalho de outra tarefa. Depois:

```powershell
git diff --cached --check
git diff --cached
git commit -m "RB-066: Automatizar jornada principal do MVP em sandbox"
git push -u origin feat/rb-066-automatizar-jornada-principal-do-mvp-em-sandbox
```

No GitHub, abra **Pull requests → New pull request**, base `main`, compare `feat/rb-066-automatizar-jornada-principal-do-mvp-em-sandbox`. Use o [modelo de PR](../../.github/PULL_REQUEST_TEMPLATE.md). Quem já tem GitHub CLI autenticado pode usar `gh pr create --base main --head feat/rb-066-automatizar-jornada-principal-do-mvp-em-sandbox --web` após o push.
