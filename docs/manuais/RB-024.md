## 4. Passo a passo da tarefa

1. Leia o schema atual: o datasource é SQLite; trocar apenas DATABASE_URL não migra para PostgreSQL.
2. Combine a transição de provider, tipos e histórico de migrations em PR próprio; preserve bases existentes e use banco PostgreSQL descartável para validar.
3. Modele lojas, integrações, identidade, consentimentos, pedidos e auditoria com FK/constraints por tenant.
4. Crie migrations reproduzíveis para o alvo e fixtures de duas lojas com identificadores repetidos.
5. Documente preparação, aplicação, validação e recuperação de dados; nunca aplique reset em banco compartilhado.

Fontes técnicas para consultar na revisão escolhida: [Prisma: migrations entre providers](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/limitations-and-known-issues). Reconfira versão e disponibilidade na data da implementação.


## 5. Como validar

Na primeira preparação, siga o [README](../../README.md) e execute `npm ci --ignore-scripts` e `npm run db:generate` antes de comandos que usem dependências. Node 22 e PHP 8.3 são as versões de referência do CI. Variáveis e segredos são locais; consulte `.env.example` e o guia do componente.

| Caso mínimo | Ação e resultado a verificar | Registro |
| --- | --- | --- |
| V1 | Banco PostgreSQL vazio recebe a cadeia correta de migrations e fixtures. | Não executado por este manual; registrar resultado e link na entrega. |
| V2 | Constraints impedem duplicação indevida e consultas não misturam duas lojas. | Não executado por este manual; registrar resultado e link na entrega. |

Execute na raiz, após produzir sua alteração:

```powershell
npm run check
git diff --check
```

Acrescente teste comportamental pertinente em `tests/*.test.ts`, incluído pelo runner atual, quando houver código novo. Configure apenas ambientes descartáveis/autorizados para banco, loja e PSP; fixtures não comprovam integração externa.

Para cada critério abaixo, preencha na entrega: preparação, ação, esperado, observado, passou/falhou/não executado e evidência. Para design/documentação, inclua revisão de leitura/links/protótipo; não crie teste de código artificial. Uma execução antiga não comprova seu commit atual.

## 7. Branch, documentação e PR pelo terminal

Se é seu primeiro trabalho, clone e configure autoria conforme o [tutorial](../../README.md). Dentro de `boopay`, com trabalho anterior salvo na branch correta e árvore limpa:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/rb-024-implementar-postgresql-transacional-e-migrations
```

Se essa branch já existe, use `git switch feat/rb-024-implementar-postgresql-transacional-e-migrations` para continuar; não execute `-c` novamente. Prepare seu documento sem sobrescrever uma entrega existente:

```powershell
if (-not (Test-Path 'docs/entregas/RB-024.md')) {
    Copy-Item 'docs/entregas/MODELO.md' 'docs/entregas/RB-024.md'
}
```

Faça os passos da seção 4 e preencha `docs/entregas/RB-024.md`: autor, issue, manual, objetivo, arquivos, decisões, preparação, passos, esperado/observado, evidências e pendências. Remova os campos de orientação do modelo e preserve versões anteriores. Para artefato externo, versione o roteiro/registro com link acessível, exportação ou capturas pertinentes; não abra PR vazio.

Antes de enviar, execute a seção 5 e confira seleção de arquivos:

```powershell
git diff --stat
git diff
git status --short
git add -- docs/entregas/RB-024.md
```

O comando acima seleciona apenas a documentação. Selecione também cada arquivo de código/teste/artefato que você criou ou alterou com `git add -- caminho/do/arquivo` (substitua pelo caminho real). Confira `git status --short` e não inclua `.env`, banco local, credenciais ou trabalho de outra tarefa. Depois:

```powershell
git diff --cached --check
git diff --cached
git commit -m "RB-024: Implementar PostgreSQL transacional e migrations"
git push -u origin feat/rb-024-implementar-postgresql-transacional-e-migrations
```

No GitHub, abra **Pull requests → New pull request**, base `main`, compare `feat/rb-024-implementar-postgresql-transacional-e-migrations`. Use o [modelo de PR](../../.github/PULL_REQUEST_TEMPLATE.md). Quem já tem GitHub CLI autenticado pode usar `gh pr create --base main --head feat/rb-024-implementar-postgresql-transacional-e-migrations --web` após o push.

Preencha no PR:

## 8. Quando pedir review e quando concluir

Peça revisão e mova para **Review** quando o PR tiver escopo conferível, documentação e validação anexadas. Resolva os comentários na mesma branch e repita os checks afetados. O autor não aprova o próprio PR. **Done** exige revisão, merge e validação do resultado integrado conforme o card/DoD; abrir PR ou publicar este manual não basta.

Se houver bloqueio, registre: passo que falhou, erro sanitizado, tentativa feita, dependência e ajuda necessária. Não simule sucesso para concluir o card.
