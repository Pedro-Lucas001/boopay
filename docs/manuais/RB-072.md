## 1. O que entregar

Produzir documento de dois prompts que falharam.

Entregue o resultado desta tarefa, a documentação do autor em `docs/entregas/RB-072.md`, validação reproduzível e um PR revisável. Uma alteração somente neste manual é documentação, não execução da tarefa.

## 2. Antes de começar

[RB-071](./RB-071.md)

Confira os artefatos/contratos dessas dependências. Se o necessário ainda não existir, registre exatamente o bloqueio no card. Trabalho paralelo pode usar interface acordada, identificando a suposição; aceite integrado exige a dependência real. Confirme seu responsável/revisor e mova para **In progress** somente ao iniciar trabalho efetivo.

## 3. Onde trabalhar

- [docs/uso-ia.md](../../docs/uso-ia.md) — já existe; leia antes de alterar.
- `docs/prompt-ops/dois-prompts-falhos.md` — caminho proposto; crie se necessário ou documente equivalente combinado com o time.
- `docs/entregas/RB-072.md` — documentação da sua execução; se já existir, preserve autoria e resultados anteriores e acrescente a nova versão.
- `docs/evidencias/RB-072/` — evidências novas sanitizadas; use apenas quando houver arquivos a guardar.

Os caminhos propostos organizam a entrega, não afirmam que componentes futuros já existem. Se outro PR criou o módulo em local diferente, reutilize-o e registre o caminho final; evite duas implementações da mesma função.

## 4. Passo a passo da tarefa

1. Selecione com os autores dois casos reais de IA que produziram resultado inadequado.
2. Guarde referência ao registro completo e evidência sanitizada de cada falha.
3. Resuma em até uma página: objetivo, prompt, falha, ajuste, resultado e validação.
4. Explique o motivo da correção e o limite que permaneceu, sem inventar melhoria medida.
5. Peça conferência dos autores e revise legibilidade no formato de entrega exigido.


## 5. Como validar

Na primeira preparação, siga o [README](../../README.md) e execute `npm ci --ignore-scripts` e `npm run db:generate` antes de comandos que usem dependências. Node 22 e PHP 8.3 são as versões de referência do CI. Variáveis e segredos são locais; consulte `.env.example` e o guia do componente.

| Caso mínimo | Ação e resultado a verificar | Registro |
| --- | --- | --- |
| V1 | Os dois casos remetem a registros reais e mostram antes/depois verificável. | Não executado por este manual; registrar resultado e link na entrega. |
| V2 | Síntese cabe no limite e preserva autoria, sem expor segredos. | Não executado por este manual; registrar resultado e link na entrega. |

Execute na raiz, após produzir sua alteração:

```powershell
npm run check:docs
git diff --check
```

Para cada critério abaixo, preencha na entrega: preparação, ação, esperado, observado, passou/falhou/não executado e evidência. Para design/documentação, inclua revisão de leitura/links/protótipo; não crie teste de código artificial. Uma execução antiga não comprova seu commit atual.

## 7. Branch, documentação e PR pelo terminal

Se é seu primeiro trabalho, clone e configure autoria conforme o [tutorial](../../README.md). Dentro de `boopay`, com trabalho anterior salvo na branch correta e árvore limpa:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c docs/rb-072-produzir-documento-de-dois-prompts-que-falharam
```

Se essa branch já existe, use `git switch docs/rb-072-produzir-documento-de-dois-prompts-que-falharam` para continuar; não execute `-c` novamente. Prepare seu documento sem sobrescrever uma entrega existente:

```powershell
if (-not (Test-Path 'docs/entregas/RB-072.md')) {
    Copy-Item 'docs/entregas/MODELO.md' 'docs/entregas/RB-072.md'
}
```

Faça os passos da seção 4 e preencha `docs/entregas/RB-072.md`: autor, issue, manual, objetivo, arquivos, decisões, preparação, passos, esperado/observado, evidências e pendências. Remova os campos de orientação do modelo e preserve versões anteriores. Para artefato externo, versione o roteiro/registro com link acessível, exportação ou capturas pertinentes; não abra PR vazio.

Antes de enviar, execute a seção 5 e confira seleção de arquivos:

```powershell
git diff --stat
git diff
git status --short
git add -- docs/entregas/RB-072.md
```

O comando acima seleciona apenas a documentação. Selecione também cada arquivo de código/teste/artefato que você criou ou alterou com `git add -- caminho/do/arquivo` (substitua pelo caminho real). Confira `git status --short` e não inclua `.env`, banco local, credenciais ou trabalho de outra tarefa. Depois:

```powershell
git diff --cached --check
git diff --cached
git commit -m "RB-072: Produzir documento de dois prompts que falharam"
git push -u origin docs/rb-072-produzir-documento-de-dois-prompts-que-falharam
```

No GitHub, abra **Pull requests → New pull request**, base `main`, compare `docs/rb-072-produzir-documento-de-dois-prompts-que-falharam`. Use o [modelo de PR](../../.github/PULL_REQUEST_TEMPLATE.md). Quem já tem GitHub CLI autenticado pode usar `gh pr create --base main --head docs/rb-072-produzir-documento-de-dois-prompts-que-falharam --web` após o push.

Preencha no PR:

- Relação: `Refs #64` para parcial/documentação; `Closes #64` apenas se a entrega cumpre todo o aceite. Isso vincula fechamento ao merge, não à abertura do PR.
- Link deste manual e `docs/entregas/RB-072.md`.
- Arquivos e resultado entregue; decisões relevantes e motivo.
- Passos/comandos exatos para o revisor repetir, com ambiente e dados sintéticos.
- Resultados observados, links de evidência e limitações restantes.
- Revisor combinado, diferente do autor; mantenha Draft se faltar parte obrigatória.

## 8. Quando pedir review e quando concluir

Peça revisão e mova para **Review** quando o PR tiver escopo conferível, documentação e validação anexadas. Resolva os comentários na mesma branch e repita os checks afetados. O autor não aprova o próprio PR. **Done** exige revisão, merge e validação do resultado integrado conforme o card/DoD; abrir PR ou publicar este manual não basta.

Se houver bloqueio, registre: passo que falhou, erro sanitizado, tentativa feita, dependência e ajuda necessária. Não simule sucesso para concluir o card.
