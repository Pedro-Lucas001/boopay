# RB-034 — Observabilidade e diagnóstico básico

Autor da implementação: Thiago Ventura. Issue [#27](https://github.com/Pedro-Lucas001/boopay/issues/27). Branch `feat/rb-034-observability`. Dados e serviços usados nos testes são locais e sintéticos.

## Resultado

- Cada resposta HTTP inclui `x-request-id` aleatório gerado pela API. Um valor enviado pelo cliente não controla o ID nem aparece nos logs.
- O Fastify registra rota, método, classe de status e duração. Erros internos incluem o mesmo request ID, sem serializar erro de banco, corpo ou credencial.
- Logs de sincronização/evento incluem `correlationId` validado a partir do event ID e podem ser cruzados com o request ID do Fastify.
- `GET /v1/admin/observability/metrics` requer Bearer administrativo e retorna contagem de requests, erros 5xx e latência média/máxima/buckets por template de rota. Usa `Cache-Control: no-store` e não retorna dados de lojas, IDs de usuários, corpos ou segredos.
- A métrica fica em memória do processo atual e zera no reinício. Não substitui retenção centralizada nem é apresentada como integração com Prometheus.
- A saúde por integração permanece em `/v1/integrations/health`. A fila de catálogo pertence ao Action Scheduler no WordPress e pode ser inspecionada em WooCommerce → Status → Ações agendadas, grupo `boopay`; a API não inventa um estado de fila que não recebe.

## Diagnóstico e recuperação

1. Leia o `x-request-id` informado na resposta e localize o mesmo ID nos logs da API.
2. Correlacione falhas de catálogo/eventos pelo `correlationId` (event ID), sem copiar token ou payload para o chamado.
3. Consulte as métricas com token administrativo apenas no servidor: `GET /v1/admin/observability/metrics`.
4. Para uma loja, consulte a saúde autenticada e verifique catálogo/último evento; no WordPress, confira sincronização, último envio e saúde em WooCommerce → BooPay.
5. Para jobs pendentes/falhos, inspecione o grupo `boopay` no Action Scheduler. Corrija a causa antes de solicitar repetição; não duplique compras nem reenvie evento com novo event ID.

`GET /health` continua sendo liveness público. As métricas administrativas são agregadas por rota, têm cardinalidade limitada e não mudam o estado de loja. A execução e os checks desta branch estão em [check.log](../evidencias/RB-034/check.log).
