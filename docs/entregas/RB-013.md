# RB-013 — HTTP assinado e validação da API

Autor: Thiago Ventura. Revisão independente e instalação no plugin: pendentes.
Issue: [#4](https://github.com/Pedro-Lucas001/boopay/issues/4).
Base: RB-011, que por sua vez depende de RB-002.

## Contrato proposto v1

POST /v1/admin/catalog/sync, Content-Type application/json, Bearer da integração.
Cabeçalhos: X-Boopay-Tenant, X-Boopay-Integration, X-Boopay-Timestamp (Unix em
segundos), X-Boopay-Nonce (16–128 caracteres alfanuméricos, hífen ou underscore)
e X-Boopay-Signature (HMAC-SHA256, hexadecimal minúsculo de 64 caracteres).
O segredo é a string signing_secret entregue pela troca de código.

Entrada HMAC, com seis linhas separadas por LF e sem LF final:

```text
v1
POST
/v1/admin/catalog/sync
TIMESTAMP
NONCE
SHA256_HEXADECIMAL_DOS_BYTES_EXATOS_DO_CORPO
```

A assinatura inclui método e caminho. Query string é rejeitada. O cliente
aceita somente a origem HTTPS configurada em allowlist externa, sem path,
usuário, senha, query ou fragmento. Não derive a allowlist da entrada da tela.
O servidor compara o timestamp em uma janela de 300 segundos, valida token
ativo e vínculo tenant/integração e persiste o nonce para impedir replay.
O corpo é limitado a 1 MiB. O cliente usa timeout de 10 segundos,
wp_safe_remote_post, TLS verificado e zero redirects.

merchant_id precisa coincidir com a credencial. Enquanto a identidade de
produtos usar SKU global no schema atual, colisões de SKU entre lojas são
rejeitadas com 403; a evolução da identidade pertence a RB-006/RB-016.
Essa restrição impede alteração cruzada, mas ainda não permite o mesmo SKU
em duas lojas. O teste cobre tanto alteração quanto exclusão indevidas.

## Integração do cliente no plugin

Incluir integrations/woocommerce/class-boopay-signed-http-client.php no
bootstrap de RB-008/RB-012 e passar credenciais obtidas pelo fluxo de conexão.
O módulo não registra hooks, não cria tela nem ativa um plugin sozinho.
Cada retry gera nonce novo; retry de transporte não substitui a idempotência
de eventos/produtos de RB-016. O módulo remove detalhes sensíveis dos erros.

O cliente depende das funções HTTP do WordPress. Os testes locais usam
substituições explícitas dessas funções e não comprovam conexão em loja real.

## Evidências locais — 2026-10-10

Windows, Node 24.18.0, Prisma 5.22.0, PHP 8.3.35 oficial com SHA-256 conferido.

```bash
npm run db:generate
npm run check
```

PHP_BINARY pode apontar ao executável PHP portátil. Na CI, PHP está no PATH.
Resultado observado: compilação e JS passaram; três PHPs sem erro de sintaxe;
seis grupos PHP passaram; links relativos válidos; cinco testes Node passaram,
zero falhas. Os testes de HTTP usam Fastify.inject e banco SQLite temporário.

Casos: assinatura válida, corpo adulterado, token inválido, tenant/integração
divergentes, timestamp antigo, replay sequencial e concorrente, merchant
divergente, SKU de outra loja protegido, upsert próprio, JSON inválido,
corpo acima do limite e token revogado. Vetor com acentos produz o mesmo HMAC
no PHP e no Node.

## Autorrevisão

- Corrigida a rota original que aceitava sincronização sem autenticação.
- Raw body preservado e hash calculado sobre bytes, sem reserializar JSON.
- Nonce persistido antes de permitir escrita; somente violação de unicidade
  é traduzida em replay. Erro de banco permanece falha, não sucesso.
- Checagem de propriedade repetida dentro da transação de upsert.
- URLs, tokens e assinaturas não são colocados no texto de evidência.
- Catalog sync ainda tem contadores/falhas do contrato original; atomicidade
  do lote, ordem temporal e identidade composta pertencem à ingestão RB-016.

## Operação e retorno

Aplicar migração aditiva de ReplayNonce. Relógios precisam estar sincronizados.
Um retry usa nova assinatura/nonce e precisa respeitar idempotência do contrato.
Manter limpeza dos nonces expirados e rate limiting no proxy antes de expor a
API publicamente. Em incidente, revogar credencial; não reabrir a rota sem auth.
Devolver código não desfaz dados e não revoga tokens automaticamente.
