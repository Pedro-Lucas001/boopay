# RB-020 — QA da entrega WooCommerce

Autor: Thiago Ventura. Issue [#5](https://github.com/Pedro-Lucas001/boopay/issues/5). Código, QA automatizada e navegação real disponíveis em PR; revisão humana, ensaio pelo apresentador e homologação da hospedagem pendentes. Não marcar aceite integral.

## Evidência executada

[Resultado WordPress](../evidencias/WORDPRESS/results.json) é a fonte das 44 verificações locais, versões, timeout medido, dados sintéticos recebidos, revogação e SHA256 do ZIP instalado. [Backend/cliente](../evidencias/RB-020/backend-local.json) registra comandos/exit codes. [QA no Chrome](../evidencias/BROWSER/README.md) registra consentimento, recarga, produto/carrinho, revogação e ações administrativas reais. [Checks plugin](../evidencias/PLUGIN/check.log) e [API](../evidencias/API-PLUGIN/check.log) preservam as rodadas anteriores.

Ambiente: WordPress 6.8.3, WooCommerce 10.2.2, PHP 8.3.35 local, Node 24.18.0 local, SQLite Database Integration 3.1.0; CI usa Node 22/PHP 8.3. Backend Prisma 5.22/SQLite. O teste instala ZIP novo via ZipArchive + activate_plugin em banco WordPress novo, usa WC CRUD e Action Scheduler real, envia via HTTPS com certificado verificado e confere a projeção da API. Não usa mocks de WordPress nesse fluxo. Falhas HTTP temporária/permanente são injetadas explicitamente; timeout é real. A CA e a permissão de loopback existem somente no runner QA; TLS não é desativado.

## Defeitos e correções da rodada

O contador inicial baseado em timestamp sofreu truncamento no adaptador SQLite e fazia a API ignorar atualizações posteriores. Foi substituído por sequência auto-incrementada, que também evita depender de relógio e garante IDs distintos entre processos. QA detectou e cobriu atualização, exclusão e última variação após a correção.

A primeira execução do lote ampliado atingiu o limite cumulativo de tempo do runner na mesma chamada CLI. O teste usa limite ampliado só no runner QA; o plugin mantém o comportamento normal da hospedagem. A confiança da CA temporária foi configurada pelo argumento sslcertificates da API HTTP WordPress, mantendo sslverify true.

A navegação real detectou que `wp_localize_script` convertia consentimento e ID de produto em strings. Substituído por JSON tipado em `wp_add_inline_script`. A matriz cobre booleano/ID inteiro e a nova instalação do ZIP foi retestada no Chrome: recarga mantém consentimento, produto e carrinho geram eventos, revogar mantém a contagem estável. A CI executa os 44 casos com SQLite e MySQL 8.4; cada job gera seu próprio resultado/versões. Homologação da hospedagem continua separada.

## Reprodução e recuperação

Siga [AMBIENTE-PLUGIN](./AMBIENTE-PLUGIN.md), execute `npm run check`, `npm run qa:evidence`, `npm run package:plugin`, `npm run qa:wordpress`. `qa:plugin` continua sendo apenas inventário/preflight e não prova instalação. O JSON WordPress corresponde ao hash efetivamente instalado; não reaproveitar resultado se o ZIP mudar.

Revogar/desconectar primeiro; parar envios; restaurar código/ZIP compatível mantendo recibos e tombstones. Banco WordPress restaurado ou sequência reiniciada exige nova integração. Revisão do time e nova execução na main integrada precedem Feito.
