# RB-011 — Conexão e credenciais

Autor: Thiago Ventura. Revisão independente: pendente.
Issue: [#3](https://github.com/Pedro-Lucas001/boopay/issues/3).
Base: branch RB-002. Esta mudança é backend, não a tela do plugin.

## Contrato proposto

- POST /v1/admin/connection-codes: Bearer administrativo configurado no servidor
  (mínimo 32 caracteres). Corpo: tenant_id, merchant_id existente, store_url HTTPS.
- POST /v1/integrations/connect: code e store_url exatamente vinculados ao código.
  Retorna integration_id, tenant_id, merchant_id, token e signing_secret uma vez.
- POST /v1/integrations/disconnect: Bearer da integração; revoga a credencial.
- Respostas com credenciais usam Cache-Control: no-store.

O código tem 256 bits aleatórios, expira em cinco minutos, é armazenado como
SHA-256 e é consumido atomicamente na mesma transação que cria a integração.
O token também fica como hash; o segredo HMAC fica cifrado com AES-256-GCM.
Tenant, loja e URL vêm do código emitido pelo administrador, não da troca.

## Configuração e reprodução

Defina DATABASE_URL, BOOPAY_ADMIN_TOKEN e BOOPAY_CREDENTIAL_KEY fora do Git.
A chave deve ter 32 bytes em hexadecimal, persistidos no gerenciador de
segredos do ambiente. Não trocar a chave sem plano de rotação/migração.
Use um token aleatório administrativo e TLS no proxy de acesso externo.

```bash
npm ci --ignore-scripts
npm run db:generate
npm run db:migrate
npm run check
```

No Windows/Prisma 5, foi necessário criar o arquivo SQLite vazio antes de
migrate deploy; o teste faz isso automaticamente em diretório temporário.
O teste cria um Merchant sintético e remove seu próprio banco ao terminar.
A emissão administrativa requer um Merchant previamente cadastrado; o
cadastro e as fixtures de RB-007 permanecem responsabilidade da dependência.

## Evidências observadas — 2026-10-10

Windows, Node 24.18.0, Prisma 5.22.0/SQLite. npm run check:
compilação, JS, links e 3 testes passaram, 0 falhas.
O teste de conexão usa banco real temporário e verifica:

- emissão sem credencial administrativa rejeitada;
- código inválido, loja diferente, reutilizado e expirado rejeitados;
- vínculo tenant/merchant mantido e resposta no-store;
- hash do token e cifragem/decifragem do segredo;
- revogação rejeita autenticação;
- duas trocas concorrentes geram somente uma credencial;
- segunda instância Prisma encontra a persistência.

## Autorrevisão e limites

A rota de catálogo ainda é a implementação original nesta branch; sua
proteção por assinatura é a entrega dependente RB-013. Não publicar este
estado como API de catálogo protegida. SQLite pode devolver falha transitória
sob concorrência; o código não deve ser considerado consumido se a transação
reverter. Monitorar/repetir somente após observar a resposta, sem criar
credenciais duplicadas. Retenção de códigos usados e rate limiting no proxy
devem ser combinados antes de exposição pública.

Migração é aditiva. Retornar o código não remove tabelas nem revoga tokens:
desative a emissão e revogue integrações conforme o incidente. Não excluir
registros reais para retornar uma versão. A integração no plugin e validação
em loja limpa estão pendentes.
